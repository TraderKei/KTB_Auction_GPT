# KTB TERMINAL — `KTB PD`(PD·비경쟁 옵션) 탭 재기획 프롬프트

> 이 문서는 코딩 에이전트에게 붙여넣어, `mockup/ktb-terminal.html`의 **`KTB PD` 탭**을
> "수집 가능한 데이터만으로 성립하는 콘텐츠"로 **재기획 → 승인 → 화면 수정**하게 만드는 프롬프트다.

> 배경·근거는 문서 하단 「부록」 참고.

## 왜 재기획이 필요한가 (요약)

현재 `KTB PD` 탭(`renderPD()`, `PD_ROWS`)은 **개별 PD(딜러명 A증권·B은행…)별 인수 실적**과
**PD별 옵션 한도·행사율**을 축으로 구성돼 있다. 그런데 그 핵심 축인 데이터가 실제로는 수집 불가다:

- `pd.option_limit`(PD별 옵션 한도) — **미공시(EST/추정)**. 데이터 사전·리스크 표에서 "비공개(추정필요), 리스크 높음"으로 명시.
- PD별(딜러명 단위) 세부 실적 — **개별 PD 단위 데이터는 공개되지 않는다는 전제**로 재기획한다.

→ 개별 PD 축을 버리고, **공개·정형으로 수집되는 비경쟁/입찰 데이터**로 탭의 콘텐츠를 다시 설계한다.

# 역할

너는 KTB TERMINAL(블룸버그형 국고채 다크 터미널)의 화면 기획 겸 프론트엔드 엔지니어다.
대상 파일은 `mockup/ktb-terminal.html` 단일 파일(HTML+CSS+JS, Chart.js)이다.
`KTB PD` 탭(탭바 `data-scr="pd"`, 렌더 함수 `renderPD()`, 데이터 `PD_ROWS`, 차트 `initCharts`의 `scr==="pd"` 블록)을
**수집 가능한 데이터만으로 성립하는 새로운 콘텐츠로 재기획**해야 한다.

# 배경 (반드시 먼저 이해)

현재 `KTB PD` 탭은 **개별 PD(딜러명)별 인수 실적 + PD별 비경쟁II 옵션 한도/행사율**을 축으로 짜여 있다.
그러나 이 축의 핵심 데이터는 실제로 수집할 수 없다:

- `pd.option_limit`(PD별 옵션 한도)는 **미공시(EST/추정)** 필드다. (`docs/DATA-DICTIONARY.md` 리스크 표: "비공개(추정필요), 리스크 높음")
- **개별 PD(딜러명 단위) 실적 데이터는 공개되지 않는다**는 것을 이 작업의 전제로 삼는다.

따라서 기존 구현(`PD_ROWS`의 딜러명·옵션한도·행사율 구조)을 **참고하거나 재사용하지 말고**,
아래 "수집 가능한 데이터"만으로 새 콘텐츠를 처음부터 기획하라.

# 절대 규칙

1. **2단계로 진행한다. 1단계(기획 개요) 승인 없이 절대 화면(HTML/JS)을 수정하지 마라.**
   - 1단계: "어떤 데이터로 → 어떤 콘텐츠(패널)를 만들지" **개요 문서만** 산출하고 멈춰서 사용자 승인을 받는다.
   - 2단계: 승인된 개요대로만 `ktb-terminal.html`을 수정한다.
2. **수집 불가 데이터를 콘텐츠의 축으로 쓰지 마라.**
   - 개별 PD(딜러명)별 실적, `pd.option_limit`(PD 옵션 한도), PD별 옵션 행사율 → **사용 금지**.
   - 미공시(EST) 값을 "추정 배지"를 달아 억지로 채우는 방식도 이 탭에서는 지양한다(신뢰도 낮음).
3. **기존 `KTB PD` 구현을 참고·복제하지 마라.** `PD_ROWS`(딜러명·opt_lim·행사율) 구조·표·차트를 그대로 옮기지 않는다. 백지에서 재설계한다.
4. **수집 가능한 데이터만 사용한다.** (아래 목록) 새 필드가 필요하면 그 필드가 어느 테이블·원천에서 실제로 공개되는지 근거를 밝혀라. 근거 없이 새 원천을 지어내지 마라.
5. **저장 단위는 억원(정수)**. 화면 표시는 조원 등으로 변환 가능하나, 데이터 층 기준은 억원.
6. **디자인 시스템·규약 유지**: 기존 CSS 변수(다크 팔레트), 패널/qbanner/blot 테이블 구조, 그리고 **모든 데이터 셀의 `data-field` / `data-source` / `data-freq` 속성 규약**을 반드시 따른다.
7. **다른 탭을 건드리지 마라.** 수정 범위는 `KTB PD` 탭 관련 코드(탭 라벨, `renderPD()`, 그 전용 데이터 상수, `initCharts`의 pd 블록)로 한정한다.

# 사용 가능한 데이터 (수집 O — 이 안에서만 콘텐츠를 구성)

원천: `MOEF_KTB`(HTML 스크래핑) / `BOK_ECOS`(REST). 상세는 `docs/DATA-DICTIONARY.md`, `docs/crawler-prompt.md`, `design/schema/schema.sql` 참조.

**비경쟁 인수 관련 (공개, 이 탭의 새 주제로 유력)**
- `auction_result.noncomp_amt` — 비경쟁인수액 **총액** (종목·차수별, 억원). *개별 PD가 아니라 종목/차수 단위 총액*
- `auction_result.won_amt` — 낙찰액(경쟁분 포함) → 비경쟁/경쟁 **비중** 파생 가능
- `auction_result.pd_count` — 참여 PD **수** (딜러명 없는 집계 수치)
- `auction_schedule.auction_type` — `comp/nc1/nc2/nc3/nc4/bb/ex` → **비경쟁 유형(I~IV)별** 분해 가능
- `auction_schedule.plan_amt` / `auction_result.won_amt` — 발행예정 대비 실적

**종목/발행 컨텍스트 (공개)**
- `bond_master` — 종목명·만기구간(2Y~50Y)·표면금리·지표물 여부
- `issuance_plan` — 월간/연간 발행계획액 (만기별)
- `redemption_schedule`, `buyback_exchange` — 상환·매입·교환

**시계열 (공개)**
- 위 값들의 **월별/만기별/유형별 집계 및 시계열** 구성 가능
- `BOK_ECOS` 시장금리(유통수익률) 시계열 — 참조축으로 활용 가능

**파생(DERIVED, 자체계산 — 표시는 가능, 배지 `DERIVED`)**
- 비경쟁 비중 = `noncomp_amt ÷ won_amt`, 비경쟁 유형별 구성비, 월별 순공급 등 raw로부터 계산되는 지표

# 사용 금지 데이터

- 개별 PD(딜러명)별 실적: `pd_allotment`의 딜러 단위 `comp_won`/`nc2_amt`/`exchange_amt`를 **딜러명 축으로** 쓰는 것
- `pd.option_limit`(PD 옵션 한도, EST/미공시), `pd.option_exercise_rate`(그에 의존하는 행사율)
- `KOFIA` 민평금리(별도 규칙상 이 프로젝트에서 취급 제외)

# 1단계 산출물 — 기획 개요 (먼저 이것만, 그리고 멈춤)

`docs/pd-tab-replan-outline.md`(신규)에 아래를 담아 **간결하게** 작성하고, 사용자 승인을 기다려라. 코드는 아직 만들지 마라.

1. **새 탭 정체성**: 탭 코드/라벨 제안(예: 기존 `KTB PD` 라벨을 유지할지, 비경쟁 중심으로 재명명할지)과 "이 화면이 답하는 질문"(qbanner 한 문장).
2. **콘텐츠(패널) 2~4개 안**: 각 패널마다
   - 패널 제목 / 부제
   - **어떤 질문에 답하는가**
   - **사용 데이터 필드**(위 "사용 가능한 데이터"에서 정확한 컬럼명으로) + 원천(`MOEF_KTB`/`BOK_ECOS`/`DERIVED`)
   - 표현 형태(블로터 테이블 / 스택 막대 / 라인 / 도넛 / 히트맵 등)
   - 파생 지표가 있으면 **산식**
3. **데이터 매핑 표**: 화면 요소 → `data-field` / `data-source` / `data-freq` 초안.
4. **버리는 것 명시**: 기존 대비 무엇을(개별 PD·옵션한도) 제거하는지 한 줄.
5. **미해결/확인 필요 사항**: 수집 가능성이 애매한 필드가 있으면 여기 적어 사용자에게 질문.

> 개요는 3~4개 콘텐츠 안을 **우선순위와 함께** 제시하되, 데이터 근거가 가장 탄탄한 안을 "추천"으로 표시하라.

# 2단계 — 화면 수정 (승인 후에만)

승인된 개요대로 `mockup/ktb-terminal.html`을 수정한다:
- `PD_ROWS`를 새 데이터 구조로 교체(또는 신규 상수 추가 + 구식 제거).
- `renderPD()`를 새 패널 구성으로 재작성. `qbanner`·`panel`·`p-head`·`blot`·`speccard` 등 기존 컴포넌트/클래스 재사용.
- `initCharts`의 `scr==="pd"` 블록을 새 차트로 교체(Chart.js, 기존 다크 옵션 `gopt()`·팔레트 재사용).
- 모든 데이터 셀에 `data-field`/`data-source`/`data-freq` 부여.
- 탭 라벨(`data-scr="pd"`) 텍스트를 새 정체성에 맞게 갱신(필요 시).
- 데이터 사전 탭(DICT 테이블)의 `pd.*` 행도 새 필드와 일관되게 갱신(제거/추가) — 화면과 사전의 정합성 유지.

## 부록: 이 프롬프트의 설계 근거

- **왜 2단계 게이트인가**: 사용자가 "화면을 수정하기 전에 어떤 데이터로 어떤 콘텐츠를 만들지 개요를 먼저 확인하고 싶다"고 명시. 그래서 1단계(개요)→승인→2단계(구현)를 절대 규칙 1번으로 강제했다.
- **무엇이 실제로 수집 불가인가**: `docs/DATA-DICTIONARY.md`의 리스크 표에서 명확히 "비공개"로 찍힌 것은 `pd.option_limit`(PD별 옵션한도)뿐이다. `pd.comp_won`·`pd.nc2_amt` 등은 사전상 "기재부 PD 실적공시"로 표기돼 있으나, 사용자가 "PD별 데이터는 공개되지 않는다"고 밝혔으므로 **개별 PD(딜러명) 축 전체를 수집 불가로 간주**하고 재기획하도록 했다. 프롬프트 초반에서 이 전제를 재확인하게 하는 라인을 넣어, 사전과 사용자 진술이 어긋나는 지점을 에이전트가 인지하도록 했다.
- **왜 비경쟁 총액 중심인가**: 딜러명 없이도 공개·정형으로 확보되는 축이 `auction_result.noncomp_amt`(비경쟁인수 총액), `auction_schedule.auction_type`(nc1~nc4 유형), `pd_count`(참여 PD 수), 그리고 이들의 만기별/월별 시계열이다. 개별 PD 대신 **"비경쟁 인수 구조·유형·시계열"**로 주제를 옮기면 같은 탭 위치에서 신뢰도 높은 콘텐츠가 성립한다.
- **디자인·규약 보존**: `ktb-terminal.html`은 모든 데이터 셀에 `data-field`/`data-source`/`data-freq`를 다는 규약과 다크 디자인 시스템을 갖고 있어(AGENTS.md 4·7항), 프롬프트가 이를 유지하도록 못 박았다.
- **범위 한정**: 회귀 위험을 줄이려 수정 범위를 PD 탭 관련 코드로 좁히고 다른 탭 변경을 금지했다.
